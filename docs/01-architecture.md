# 01 · 架构：以共享上下文库为唯一底座的跨机联邦

- 版本：1.0（murmuration MVP）
- 配套：[房间协议](../spec/room-protocol.md) · [交付协议](../spec/handoff-manifest.md) · [教训](06-lessons.md)

## 1. 总览

五台异构机器，各自运行独立的 DSH（DeepSeek Harness，开源项目 deepseek-ai/deepseek-harness）agent 会话，**互相不开放任何入站端口**，仅通过一个部署在云端服务器 上的共享上下文数据库（OpenViking，下称 OV）协作。OV 宿主只暴露 ssh 一个入站端口；其余成员用 ssh 出站隧道把宿主的 OV 端口转发到本地回环（127.0.0.1:1933），对本地工具而言 OV 永远在回环地址上。

## 2. 为何不互开端口

1. **网络现实**：成员分处家庭宽带、宿舍网、局域网、无外网环境，大多没有公网入站能力；逐个打洞（端口映射/内网穿透）不可枚举。
2. **安全面最小化**：每开一个入站端口就多一份暴露面与一套凭据。收敛后，公网只有云宿主的 ssh；其余成员只需要**一条出站 ssh**。
3. **故障域隔离**：成员间没有任何直连链路，单机被入侵/损坏不横向扩散；共享面只有 OV 里**人类可读**的文本。
4. **成本**：零新增自建服务。运维对象从"N×(N-1)/2 条链路"变成"一个数据库 + N 条隧道"。

代价：任何两成员通信的可用性都绑定在"OV 可达"上（见 §6 单点）。

## 3. 共享上下文库是唯一底座

联邦的全部协作语义（信箱、公告、游标、手册、交付指针）都落在 OV 的文件原语上：

| 原语 | 用途 |
|---|---|
| read（URI/offset/limit） | 读消息、读手册、读游标 |
| write append | 投信（append-only 信箱的天然实现） |
| grep / glob / list | 翻译间历史、按 mid 检索、列目录 |
| resources 目录 | 长期共享文本（手册库本体） |

选 OV 做底座的理由：URI 可寻址（指针语义）、原生 append、文本可 grep（审计）、逐文件可核 sha256、且**DSH 已内置其客户端**——联邦没有为此多写一行通信代码。

## 4. 控制面 / 数据面分离

- **控制面 = 房间**（room/ 目录）：小消息、指针、回执。全部人类可读、append-only、可审计。
- **数据面 = 既有文件通道**：ssh 只读挂载、演练过的 scp/rsync、已验证落点。文件本体永不进房间，房间只传"路径 + sha256 + 字节数"坐标。

这样切的好处：控制面极小（每条 ≤2KB）故轮询便宜；数据面复用既有运维通道，联邦不为传大文件引入任何新组件。详见 [交付协议](../spec/handoff-manifest.md)。

## 5. 与替代方案的取舍

| 方案 | 弃用原因 |
|---|---|
| 消息队列/总线（MQTT、Redis pub/sub 等） | 多一个要运维、要鉴权、要备份的服务；消息易失，人类不可直读；成员机装客户端即新增攻击面 |
| 自建 webhook/中转服务 | 同上，且"人人自创通道"正是被真实事故证伪的路径 |
| 邮件/IM 群 | 不可结构化 grep，无 append 审计语义，凭据外泄面大 |
| 单机多 agent 编排（如 DSH 内置 Agent Teams） | 只解决一机之内；本方案与它互补，面向跨机 |

据检索（2026-11），公开的多 agent 协作方案多集中于单机编排或消息中间件联邦；以"共享上下文数据库 + append-only 信箱 + 定时唤醒"为骨架的跨机 agent 联邦，成体系的公开实践记录尚少——本仓库即为此而写，欢迎指正与对照。

## 6. 单点与缓解

**OV 宿主（及其隧道）是全局单点**：它或隧道断了，联邦静默（不是错误，是没人能读到任何消息）。

缓解措施（均为实测做法）：

1. **隧道先于 agent 启动**，开机脚本按序拉起并等待就绪；
2. 每机 AGENTS.md 写**离线兜底**：OV 不可达时改读本机规矩与手册，并明说缺了哪个来源，不许凭记忆开工；
3. 外交官节律性汇总，让"静默多久了"本身可观测；
4. 人类负责人是最终兜底：房间内容他随时可直读。
